ISSUE IN BRIEF
After upload blobs shrank from 16 MiB to 4 MiB, the backend needed a review for costs that grow with blob count. Found per-object deletes exceeding batch limits, a rate limit that throttles restores, and a browser download that kept less data in flight.

HOW DID YOU DEBUG
- I had said the backend was missing: wrong, my first `find | head -100` listing cut it off. Read worker.js (blob PUT/MPU/commit/GET), pending.js,
  autodelete.js, users.js (authenticateUser), services.js (handleVaultFile), page.js, wrangler.jsonc. Ran the backend tests (pending 9 + backend 10 groups).
- Server limits are fine for 4 MiB blobs: MAX_BLOBS 200000 (32 GB / 4 MiB = 8192), single PUT <= 90 MiB, token check is HMAC only, one D1 UPDATE
  (touchPending) per blob, list pages of 1000, commit counts blobs via list.
- Found three things that scale with the number of blobs:
  1. autodelete.js deleteLinkObjects: one R2 delete PER OBJECT inside Promise.all. 10 GB = 2560 deletes in one invocation (nuke, Stop, expiry
     alarm in the Durable Object) - above the 1000-subrequest limit I know for Workers/DOs (limits recalled, not checked in the docs), so a wipe could stop half-way and leave blobs (and cost).
  2. services.js handleVaultFile (restore of Backup / Saved / Snapshot): authenticateUser per blob, and AUTH_LIMITER allows 30 per 60 s per IP.
     Already a problem at 16 MiB (~30 blobs/min = 480 MB), 4x worse at 4 MiB (~120 MB). The client retries 4 times, then reports "Download failed".
  3. page.js browser download fetched 4 chunks at a time: with 4 MiB chunks that is 16 MiB in flight instead of 64 MiB, so slower.
- tests/e2e_pending.sh against this backend: flaky in this sandbox for ORIGINAL and new code alike (13 failures, then 1, then 12 on identical code;
  a fresh E2E_DIR matters) so it is not evidence either way. Unit tests are reliable and pass.

CAUSE
Per-blob costs (subrequests, rate-limit tokens, parallelism) that were harmless at 640 blobs/10 GB become 4x larger at 2560.

FIX
- autodelete.js: deleteKeys() = R2 batch delete, up to 1000 keys per call.
- users.js authenticateUser(..., opts.limiter), services.js handleVaultFile uses FILE_LIMITER (new binding in wrangler.jsonc: 600/60 s,
  namespace_id "1007" (1001-1006 are used by other workers); if the binding is missing it falls back to AUTH_LIMITER, so nothing gets weaker by accident). Trade-off: guessing
  credentials through that one route is allowed 600/min/IP instead of 30 (API keys are SHA-256 of random secrets, not human passwords).
- page.js: ~64 MB in flight whatever the chunk size (4..16 workers).
- tests: pending.test.mjs groups 10 (2500 blobs wiped in a few delete calls) and 11 (limiter choice); mock_env.mjs list() cursor is now key
  based like R2 (the old index cursor skipped objects when the caller deleted what it listed).
- Left alone on purpose: touchPending (1 D1 write per blob; 4x more, still negligible), holdings()/measureUpload() list pages (3 pages of 1000
  for 10 GB), ux pipeline (its chunks stay 16 MiB).
