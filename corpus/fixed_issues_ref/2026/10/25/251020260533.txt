1. ISSUE IN BRIEF
Merging the v1a and v1b branches (BB-251020262145-1..3 and BB-241020261928-1, BB-241020262040-1..4) broke Settings screens that are sourced on their own: settings_ui.sh called _st_desc_prepare, which lives in settings_desc.sh that only the import file loads, so the harness of tests/stale_size and the main-header check of tests/hints failed with an arithmetic error and a missing header.

1. HOW DID YOU DEBUG
Ran tests/run.sh fast on the merged tree: stale_size and hints failed. Ran both on base, v1a and v1b: they pass on base and v1b and fail on v1a alone, so v1a introduced it and its session had no tests/run.sh. Read tests/stale_size/harness.sh (sources only viewport.sh and settings_ui.sh) and found _ST_DESC_N empty, so `rows - 12 - _ST_DESC_N` is a syntax error. e2e_pending and e2e_services source settings_ui.sh the same way but are skipped here (../fileapi repo not found), so they are NOT verified.

1. CAUSE
A hidden load-order dependency: settings_ui.sh needs settings_desc.sh but does not load it or degrade without it, and three callers (stale_size harness, e2e_pending, e2e_services) source settings_ui.sh alone.

1. FIX
settings/bashbasicsbyvk_settings_ui.sh: _st_draw calls _st_desc_prepare only when it is defined, otherwise sets the three description variables to "no description"; the two `?` handlers call _st_desc_show only when it is defined. tests/settings_desc.sh (4) draws a screen with no description file loaded. Lesson: a file that another file depends on loads it or degrades without it (AGENTS rule 10).

2. ISSUE IN BRIEF
The Settings description block (BB-251020262145-2) changed height with the highlighted row (a long text, a short text, none), so each redraw moved the prompt up or down a row and left a blank row under it; the mouse wheel on the last screen row was then handed back to the terminal (tests/mouse "wheel on the prompt row stays with the menu" failed).

2. HOW DID YOU DEBUG
Ran tests/mouse alone on base (pass, twice), v1b (pass) and v1a (fail): the failure comes from v1a. Replayed the test steps in a pty and printed the screen with row numbers: the Settings prompt is on row 30 after opening, and on row 29 with a blank row 30 after the highlight moves to a row whose text is one line shorter. Confirmed it is not the loading bar by running with VK_SMARTLOAD=0 (same failure).

2. CAUSE
_st_desc_prepare gave the block exactly the lines of the highlighted row's text. The Settings block is erased and redrawn by row count, so a block whose height changes with the row cannot keep the prompt on one screen row.

2. FIX
settings/bashbasicsbyvk_settings_desc.sh: new _st_desc_height computes, once per screen and size, the tallest text (rows and screen text, capped at a third of the screen); _st_desc_prepare pads every row's block to that height. tests/settings_desc.sh: the block has one height on every row, a shorter text is padded; made red by removing the padding, restored.

3. ISSUE IN BRIEF
The loading bar of BB-251020262145-1 scrolled the whole screen up by one line whenever it appeared while the cursor was on the last screen row (for example the "Starting" bar on a slow start): the top header row was pushed off the screen and stayed lost.

3. HOW DID YOU DEBUG
tests/hints failed on the merged tree only with smartload on (VK_SMARTLOAD=0 passed, base passed). Forced the bar with VK_SMARTLOAD_GRACE_MS=50 and read the screen: the first header row was gone and "Starting…87" lines were on the screen. The "87" is ESC 7 / ESC 8 printed as text: tests/paste_input/vt.py (the shared test terminal) did not implement DECSC / DECRC. The scroll itself was read from the code: the first frame sent ESC D then ESC [ 1 A, and ESC D scrolls on the last row.

3. CAUSE
Two causes. The product: the bar made sure a row existed below the cursor with ESC D, which scrolls the screen when the cursor is on the last row, and the wipe did not scroll it back. The test terminal: it ignored ESC 7 / ESC 8, so any frame of the bar garbled the screen under load.

3. FIX
engine/bashbasicsbyvk_smartload.sh: no ESC D / ESC M any more. The bar goes one row down with ESC [ 1 B (it stops at the last row, where the bar takes the cursor's own row), drawn and wiped between save / restore cursor; nothing scrolls. tests/paste_input/vt.py: ESC 7 / ESC 8. tests/smartload/pty_test.py checks that no scrolling sequence is ever sent; made red by putting ESC D back. Not covered: an external program writing straight to the terminal during a wait can still leave one ghost bar row (as in the original note).

4. ISSUE IN BRIEF
Tests relied on the old loading bar's output as a side effect: tests/mouse tab_click returned as soon as the harness saw 0.2 s of silence, and the -u screen is silent for about half a second while it fetches tags, so the tap on the second tab was read from a half-painted screen; tests/choose read the screen right after the title appeared, before the rows were drawn.

4. HOW DID YOU DEBUG
Bisected: base plus only v1a's upgrade.sh (the removed _lb_run wrapper) failed the -u tab case. A probe showed the tags list arriving about 1 s after the tap while the old bar had kept the harness waiting. Then ran the whole suite with VK_SMARTLOAD_GRACE_MS=50 so the bar shows on every wait: only the second tab tap failed, because the helper checked the tab name before the rest of the screen was painted.

4. CAUSE
Waits by silence instead of by condition (AGENTS tests rule 1): the animated bar had been keeping the harness waiting.

4. FIX
tests/mouse/mouse_test.py tab_click waits for the tab bar, taps, waits until that tab is the current one and the screen is quiet. tests/choose/choose_test.py waits for the rows. Both pass in normal mode and with the bar forced on every wait.
