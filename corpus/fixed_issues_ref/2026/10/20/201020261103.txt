1. ISSUE IN BRIEF
After pastes were flattened to one row, multi-line pasted text became a single clipped line. Line breaks should be kept and the full text shown across wrapped rows.

1. HOW DID YOU DEBUG
Watched the user's screen recording (Termux): the pasted text sat on ONE `Select:` row, shown clipped with a leading "<".
Confirmed in code: _bvk_paste_clean turned line breaks into spaces and _bvk_fit_input drew one clipped row.

1. CAUSE
My earlier fix flattened line breaks and forced one row for every input.

1. FIX
_bvk_paste_clean keeps line breaks (CR dropped, tab -> space, other control bytes dropped). New _bvk_row_multi (viewport.sh):
a text that has line breaks or does not fit one row is drawn in full as a block of wrapped rows starting on the prompt row
(window of at most 6 rows that follows the cursor); everything that fits one row still uses the old one-row path.
Used by _print_input_line (browse), _multi_print_input_line, _sm_input_fn. Typed-line prompts (_cm_line_edit) and the settings
Select row stay one logical line: there a paste's line breaks become spaces (settings Select row is a single row, cursor at end).

2. ISSUE IN BRIEF
With a long pasted text shown as one clipped row, pressing Left moved the cursor onto the Select label because the visible text window never scrolled with the cursor.

2. HOW DID YOU DEBUG
Wrote a small terminal emulator (tests/paste_input/vt.py) and drove the real app in a pty: paste 1500 chars, press LEFT 150
times: the cursor went to column 0 (onto the label) 79 times while the text window never moved.

2. CAUSE
The left/right handlers of the loops (browse, multi picker, smart menu) only printed ESC[1D / ESC[1C and changed _pos. The
one-row view is a clipped window (_BVK_FIT_S) that is only recomputed on a redraw, so the cursor left the window and moved over
the prompt. (The wide-character case was also wrong: 1 column per character.)

2. FIX
_bvk_cursor_to NEWPOS REDRAW_FN (viewport.sh): a one-row text moves the cursor by the real display width of the character; a
block is redrawn (the cursor moves across rows, the window scrolls). Used by all left/right handlers.
Up/down/PgUp/PgDn/Home/End call _bvk_blk_park first (cursor back on the block's first row) because list repaints are
row-relative; _sync_highlight_from_buf and _multi_sync respect that.

3. ISSUE IN BRIEF
Add a maximum accepted input length (2000 characters at the time) for every prompt: oversized typing or pastes must be refused with a message and a redraw, including pastes that arrive in several chunks.

3. HOW DID YOU DEBUG
pty tests (tests/paste_input/ui_test.py, run.sh): 2001-char paste, 1990 + 20 chars, 1999 + 2 typed chars, 100000 chars, with and
without bracketed-paste markers. Found that without markers a big paste arrives in chunks: the head was refused but a small tail
chunk was accepted (a partial paste).

3. CAUSE
No limit existed; the unmarked-paste fallback decided per chunk instead of per paste.

3. FIX
_BVK_MAX_INPUT=2000, _bvk_room / _bvk_too_large / _bvk_notice / _bvk_paste_drain (viewport.sh): a paste or typed key that would
make the input longer than 2000 characters is not inserted; the row is redrawn and a red "Too large: N characters (limit 2000).
Not accepted; nothing was changed." line is shown until the next key. The unmarked-paste fallback now waits until input has been
quiet for 60 ms (the whole paste is one unit) and after a refusal drains the rest of it. Applied in browse, multi picker, smart
menu, typed-line prompts (_cm_line_edit: this includes y/n and free-text prompts: nothing there may exceed 2000 either) and the
settings Select row (shown in the prompt text). Not exercised by running: the smart-menu loop.
Lesson: always check the size BEFORE any ${var//x/y} (quadratic in UTF-8).
