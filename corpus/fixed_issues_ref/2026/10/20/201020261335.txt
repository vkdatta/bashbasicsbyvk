ISSUE IN BRIEF
Organising a Google Drive folder by extension created the folders but left them empty and sent every file to the Drive bin, and it took about 300 seconds. Moving files into a folder created in the same sync was treated as delete plus upload.

HOW DID YOU DEBUG
Read bashbasicsbyvk_organise.sh: it is a plain `mv` of the files into new folders. Read push_round in bashbasicsbyvk_gd:
move detection (same inode) only looked at the top-level "new" entries. Files inside a folder created in the same step
are only discovered later by walk_new, so they were never matched as moves. Reproduced with a fake rclone (not a real
Drive): before the fix, mkdir+mv gave copy+delete; after the fix it gives moveid/moveto only. The real-Drive effect is
inferred from the user's sync line, not observed.

CAUSE
Moving files into a NEW folder was treated as "old file deleted" + "new file uploaded". Deleted = Drive trash; for Google
files the "upload" was a copy by ID whose result the user does not see; for not-downloaded files the upload is refused
(placeholder), so nothing replaced the trashed original. This bug existed before the Google-native change; I did not test
moves into new folders after changing this code.

FIX
push_round: new folders are expanded first and their files are matched to vanished files by inode (moves). Safety nets:
a vanished file whose new twin was refused as a placeholder is not trashed; trashing Google files always asks
(BVK_GD_CONFIRM_NATIVE_DELETE=0 turns it off). Lesson: any "delete + create" must be proven to be a move before deleting.
