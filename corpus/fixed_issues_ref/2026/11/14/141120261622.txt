ISSUE IN BRIEF
Typed-line prompts were still not one thing after the 11/12 template work: the loop, the drawing and the suggestion row were copied five times (main Select:, the item/group picker, smart menus, Settings + choice boxes, the line editor behind _bvk_read / bashbasicsbyvk_ask). So a fix reached only the loop it was made in: tap never reached the line editor (Git Push "Enter choice" / commit message), the suggestion was drawn BELOW the text in typed-line prompts and ABOVE it in menus, pasted line breaks were flattened to spaces in some prompts and kept in others, and in Git Push a typed u or q at the commit message was committed as the message instead of going one question back.

HOW DID YOU DEBUG
Read all five loops side by side: they share one skeleton (setup raw keys + paste + mouse, read a byte with an idle tick, ESC sequence -> paste / mouse press / wheel / editing key / named key, byte -> paste burst / editing key / type, teardown) and differ only in what a key DOES. Found three hidden couplings by reading, not by guessing: _bvk_room was hard-wired to the globals _buf/_pos (so the line editor, which uses _ce_buf, could never share the length limit), the line editor had its own escape reader with a shorter timeout and no mouse decode, and the tap code reads _BLK_* row geometry that only the shared renderer sets (the line editor had its own renderer). Proved each bug with a pty test that FAILS on the original code: prompt_test.py (tap, suggestion above, pasted line break, on every prompt kind) and chain_test.py (the real Git Push commit functions with u / q / @u). Regressions found by running the existing suites against the original tree and diffing the inner FAIL lines: the choice-box command lookup (_cm_ctx_find counts unlisted frames as "inside a flow"), a nested loop inheriting the outer loop's hooks through dynamic scope, Settings' _st_back flag being checked at the start of a screen opened from a leaving handler, a prompt wider than the screen (wrap_input), the stand-alone deps installer not sourcing viewport.sh.

CAUSE
Nothing owned the typed line as a whole. The helpers (_te_esc, _te_byte, _bvk_prompt_tap, paste helpers) were shared, but each loop had to remember to call every one of them, in the right order, with its own draw function, so every fix drifted. The drift test only checked that function NAMES appeared in a file. A stand-alone tool had no way to say "u = one question back": the ask door had no back signal and its command layer was off, so u / q were text.

FIX
ONE LOOP and ONE DRAWER in viewport.sh: _bvk_edit_run (keys, paste + limit, mouse + hand-back, tap, tick, WINCH, raw setup/teardown; re-entrant, restores what it found) with hooks (_ED_*; `local $_BVK_ED_HOOKS` first so a nested loop starts clean) and _bvk_draw_input (cursor / selection, rows of a long text with line breaks kept, one scrolling row, tap geometry). All five loops now run them: browse.sh, viewport.sh (picker), smartmenu.sh, cmdmap.sh (_cm_line_edit, ~200 lines removed), settings_ui.sh (_st_readkey replaced by hooks). The suggestion sits above every prompt: _bvk_hint_area_on reserves it, _input_hint_sync (moved to viewport.sh) fills it, _bvk_hint_paint paints it. One paste function (_bvk_edit_paste). _cm_ctx_find skips the engine frames. A prompt wider than the screen is printed on its own row first. bashbasicsbyvk_ask / .py: -b (u exits 4 / raises Back), u and q as navigation words with the shared footer, @u literal; bashbasicsbyvk_gitpush: version -> message -> confirm are _mc_steps (u = one question back, typed text kept). drift.sh now enforces one loop, one drawer, one tap, clean hooks, and that chained tool questions are steps (PENDING_CHAIN is empty: gitpush, localhost and recover_creds.py are steps; the ask door gives u / q to a secret too, -S starts a re-asked answer selected, bashbasicsbyvk_ask.steps is the Python twin of _mc_steps).
