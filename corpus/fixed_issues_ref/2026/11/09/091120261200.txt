1. ISSUE IN BRIEF
Every place that accepts typed input (main Select: prompt, number picker, smart menus such as the file-action menu, typed-line prompts such as rename, Settings and choice menus) kept its own copy of a tiny editor: insert, Backspace, Left, Right. Selecting text (Shift+arrows, Ctrl+A), Ctrl+arrows by word, Delete, Home/End with Shift, cut / copy / paste (Ctrl+X / C / V), word delete and undo did nothing, or behaved differently from one prompt to the next.

1. HOW DID YOU DEBUG
Listed every raw key reader (grep read -rsn1 / stty -icanon): _read_choice_raw (browse), _multi_prompt_loop_raw (viewport), _sm_run (smartmenu), _cm_line_edit (cmdmap), _st_readkey / _st_run (settings_ui; choose.sh uses _st_run). Read how each edits _buf/_pos, how _bvk_fit_input / _bvk_row_multi / _cm_edit_draw draw the line, and the "=" live filter in filter.sh. Wrote tests/textedit/textedit_unit.sh (64 checks, no terminal) and tests/textedit/textedit_pty_test.py (real app in a pty). The pty test first failed in a way that looked random: Ctrl-Z never arrived and Ctrl-C killed the app. Logged the terminal flags from inside the app and from the harness: bash's `read -n1` switches ISIG back on while it waits, so Ctrl-C is SIGINT and Ctrl-Z is SIGTSTP, never a byte (verified with a minimal bash read in a pty). A trap on INT / TSTP fires at once even inside a blocking read. Also drove the rename prompt, the file-action menu and a Settings screen by hand in a pty. Ran the fast tier and mouse / hints / paste_input / nav_back / wrap_input / cheatcode on the untouched original and on the change: the same six fast tests (choose_plain, delete_confirm, deps, github_upgrade_shared, hints, settings_desc) and mouse fail on both, nothing new fails. Real Termux soft-keyboard behaviour, the system clipboard tools (termux-clipboard-*, xclip, wl-copy) and OSC 52 were NOT run, only the app's own clipboard path.

1. CAUSE
No shared text-edit layer: five key loops each hand-wrote the same four keys, so nothing richer than Backspace / arrows could exist anywhere without five separate edits. Shift+arrows and Ctrl+arrows were even decoded to plain arrows by _key_name, Delete (ESC[3~) was ignored in the list loops, and Ctrl-C / Ctrl-Z cannot be read as bytes through `read -n1`.

1. FIX
New engine/bashbasicsbyvk_textedit.sh (loadmap [bg]): chord decoder (CSI with modifiers, kitty CSI-u, xterm modifyOtherKeys, Alt+B/F/D/Backspace), selection model (anchor + the text it belongs to, so a line set by hand drops it), _te_apply (one switch for every editing key), word / line helpers, undo / redo, clipboard (termux, pbcopy, wl-copy, xclip, xsel, clip.exe, OSC 52, else the app's own), _te_hl for reverse-video drawing, and _te_begin / _te_end (an editor stack that also catches SIGINT / SIGTSTP while an editor is open: Ctrl-C copies the selection, with nothing selected it is still the interrupt; Ctrl-Z undoes). Contract for a loop: _te_begin BUF POS MODE REDRAW EDIT PASTE, _te_esc / _te_byte per key, _te_insert for typing and pasting, _te_end at exit. MODE list keeps plain Up / Down / PgUp / PgDn / Home / End (and Left / Right / Ctrl+A / Ctrl+E on an EMPTY line) for the list. Wired into browse.sh, viewport.sh (also _bvk_room, _bvk_fit_input, _bvk_row_multi), smartmenu.sh, cmdmap.sh (new _cm_edit_refresh), settings_ui.sh (cursor pos + posb, _st_type / _st_drop_sel / _st_edited / _st_paste_text; typed settings text is now editable in the middle). filter.sh: _filter_on_backspace replaced by _filter_resync (any edit of a "=" filter line re-applies it). _3bvk_import_deps.sh and five test harnesses source the template. Lesson: a loop that must receive Ctrl-C or Ctrl-Z cannot rely on read -n1; and a nameref API must take its arguments in one documented order (the first wiring swapped MODE and BUFVAR).

2. ISSUE IN BRIEF (follow-up, same day)
Several yes/no questions were still bare typed prompts instead of the native yes/no menu: git push (infinity stones) `[y/n]`, localhost `(Y/N)` twice, `delete` ("Type 'yes'"), `erase` ("(yes/no)"), xtract (python `input("(y/n)")`) and the Google Drive tool (python `ask_yes` on /dev/tty).

2. HOW DID YOU DEBUG
grep over script/ for [y/n] (y/N) (Y/N) yes/no, `read -p`, `input(`, `tty.write`: found the six files above (deps.sh already asks the native menu and keeps one plain line only as fallback). Tools that run as their own process cannot call _bvk_yn directly: sourcing the app's engines from every tool is forbidden (AGENTS rule 3) and a first try with the minimal import (settings_ui + choose only) drew the menu but lacked _term_cols / _bvk_paste_burst, so the keys were never accepted. Fixed by one small tool with its own import file that also loads viewport.sh. Verified in a pty: Yes 0, No 1, bare Enter ignored, q = 2.

2. CAUSE
Each of these tools had its own hand-written question. A stand-alone process had no shared yes/no to call, so every author wrote one.

2. FIX
New tool `bashbasicsbyvk_yn "Question?" [-t Title] [-i emoji] [-c]` (exit 0 yes, 1 no, 2 no answer, 3 not installed) + `_3bvk_import_yn.sh` + python door `bashbasicsbyvk_yn.py` (`ask(question, title, icon)` -> True / False / None). git push, localhost, delete, erase, xtract and gd call it; the plain line stays only as the fallback of a broken install. Quitting the menu is "no answer", never an answer: git push dies "No answer." instead of making the repository public. tests/yn/yn_test.py checks the tool, three converted tools and lints that a bare y/n prompt may exist only in a file that also asks the native menu (it flags exactly these six files on the original code). Not converted (not yes/no): create's "(d)irectory or (f)ile", xtract's (t/l) and (1/2) choices, gen_sql's "choice 1/2/3/4".
