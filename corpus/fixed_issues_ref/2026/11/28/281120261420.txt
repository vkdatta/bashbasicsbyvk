1. ISSUE IN BRIEF
Carpet animation was visible only in the Transfer picker. Every other screen is drawn by the viewport from its row cache in about 1 ms, so it looked like pop.

1. HOW DID YOU DEBUG
Read how the Transfer picker draws: it PRINTS its rows one at a time (_pick_rows_raw), then the menu layer (smartmenu.sh, "wipe the already-printed copy") erases that copy and redraws the list through the viewport. The main list (script/o) goes straight through _vp_render_fresh. A first attempt added a fixed per-row sleep; it was wrong (a different look, and it re-rolled over the Transfer picker's own roll) and is removed.

1. CAUSE
Carpet only existed where rows were built one by one (the Transfer picker). The viewport formats everything first (_vp_prime_rows) and only copies cached text to the screen.

1. FIX
viewport.sh: when a fresh screen rolls (anim=carpet), _vp_row_text skips the row cache, so every row is built from the item the way the Transfer picker builds it, and _vp_el writes it the moment it is built. No sleep, no timer. pop unchanged (one write). Arrow keys, resize and filter repaints always pop. smartmenu.sh: when the Transfer picker has just rolled its own rows (_BVK_STREAM_ROLLED, set in _pick_rows_raw, cleared in _sm_reset), the takeover redraw pops instead of rolling again, so the picker's carpet is left as it was; every other menu rolls through the viewport. settings_desc.sh: Animation texts say what carpet really does.

VERIFIED: bash -n on the changed files; a run of the real _vp_row_text / _vp_roll_set / _vp_el showing carpet bypasses the cache and writes per row, pop uses the cache, an in-place repaint never rolls. Not run: the full app in a real terminal, so how fast it rolls on a device is not measured.
