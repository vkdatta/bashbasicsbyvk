1. ISSUE IN BRIEF
On the main list, Down highlights an item and puts its number on the Select line; Backspace then erases the number but the item stays highlighted.

1. HOW DID YOU DEBUG
Read corpus BB-211020260830-4 and BB-251020261341-3 (the same symptom for typed numbers). Read _hl_typed_clear (viewport.sh), _sync_highlight_from_buf, _rc_nav and _nav_jump_to (browse.sh): the arrows set _hl_index and _buf but never _HL_TYPED, so _hl_typed_clear found "not typed" and kept the highlight. Ran the real app in a pty at 60 columns (Down, then Backspace): before the change the row repaint kept the highlight, after it the row is repainted plain. Checked from the redraw bytes, not from a colour screenshot.

1. CAUSE
Only a number typed by hand was marked as "the highlight came from typing"; the number an arrow key echoes onto the line was not, so erasing it did not drop the highlight.

1. FIX
browse.sh: new helper _nav_echo_hl (sets _buf, _pos and _HL_TYPED from _hl_index) replaces the three copies in _rc_nav (up, down) and _nav_jump_to (pgup, pgdn, home, end). Lesson: every place that echoes the highlight onto the line must also say it is an echo.

2. ISSUE IN BRIEF
Between the footer and the Select line the main list and every other menu with a typed prompt had no gap: on a wide screen the suggestion sat directly under the footer and directly above Select, and with no suggestion there was one blank row; Settings and Home (_st_draw) already showed a blank row, the suggestion, then a blank row. Wanted the same clean look everywhere.

2. HOW DID YOU DEBUG
Rendered the real app in a pty (60 and 120 columns, 20 and 40 rows): main list, fx, Home, Settings, the create menu, the goto prompt and the date picker, idle, with a typed letter and after erasing it. First version reserved a fixed 3-row area: the person pointed out that Settings shows ONE blank row when idle and grows the gaps only while a suggestion shows, so a fixed reservation (3 blank rows idle) was wrong. Reworked to the same behaviour in the shared drawer. Settings and Home (_st_draw) were not changed.

2. CAUSE
The reserved suggestion area was only as tall as the suggestion and the painter used its first row, so nothing separated the suggestion from the footer or from the prompt.

2. FIX
viewport.sh: the area is one blank row when idle. _bvk_hint_paint sizes it to 1 + suggestion rows + 1 (the last gap only on screens of 24+ rows) and _bvk_hint_resize moves the prompt: growing scrolls the screen with newlines then inserts blank rows above the prompt (ESC[L), shrinking deletes rows above it (ESC[M), so the typed text and a multi-row text move with it and nothing is redrawn. _vp_hint_n is the rows it has NOW (read by _vp_dist, the mouse code and _blk_h, which resize keeps current); _vp_hint_max is what the page is sized for (_vp_geometry), so growing never pushes the block off the screen; _vp_hint_cap is how many rows a suggestion may use (1 wide, 2 narrow). _bvk_hint_leave gives the rows back on Enter so the scrollback keeps footer / blank / "Select: text". The typed-line editor (cmdmap _cm_line_edit) uses the same area but does not touch the viewport's _blk_h (_vp_hint_trk=0). The new variables are made local with _vp_hint_n (cmdmap, xui borrow list). tests/pty/lib/vt.py learned ESC[L / ESC[M. Idle: 1 blank row under the footer on every prompt; typing: blank, suggestion, blank. Not covered: a suggestion while a multi-row text is typed (none is painted then; the rows stay as they were). The templates static check is order-dependent (it fails on the untouched upload in about one run in three); the menu_templates pty script fails on the untouched upload here (no advert file).
