ISSUE AS DEFINED BY USER
On Android (Termux), `do-` ("Paste link to import (include the #k=... part):"): the link is pasted ONCE but the screen fills
with the prompt + the start of the link about 60 times in a row ("🔗 Paste link to import (include the #k=... part): https://...
🔗 Paste link to import ... https://..." and so on), the last one holding the whole link. Not seen on Linux. Asked: why, check
the same issue across the repo, fix all of them, and record it in the corpus.

HOW DID YOU DEBUG
1. grep "Paste link to import" -> staging/!buffer/fileapi/1 upload/bashbasicsbyvk_staging_upload.sh, handle_do_import:
   `read -e -r -p "🔗 Paste link ..." link`. That is the app's own `read`, not the builtin: engine/bashbasicsbyvk_smartmenu.sh
   read() -> _cm_read_fallback -> _cm_text_read -> _cm_line_edit (engine/bashbasicsbyvk_cmdmap.sh), a hand-made one-key-at-a-time
   line editor (live hint row under the prompt).
2. _cm_line_edit redraws after EVERY key with _cm_edit_draw: `\r \033[K <prompt><text>` then `\033[<n>D` to put the cursor back.
   That only works while prompt+text fit ONE terminal row. The prompt alone is 52 cells (emoji = 2) and the link is 129 chars, so on
   a phone-width screen (~40-60 columns) the row wraps. \r, \033[K and \033[nD only act on the row the cursor is on (the last wrapped
   row), so each key prints a fresh prompt+text one row lower and the old rows stay. A paste = one key per character = the spam.
   On a wide Linux terminal short input never wraps, which is why it looked Android-only (a narrow Linux window does the same).
3. Reproduced it: new tests/wrap_input/{harness.sh,emu.py} run the real editor in a pty with a small VT emulator at a chosen width.
   Original code, link pasted: 3 prompt rows at 30 cols, 4 at 40, 6 at 50 and even 9 at 80 cols. Same symptom as the user's paste.
4. Searched the repo for the same pattern (a redraw that does \r + erase-line + prompt + typed text + \033[nD):
   _cm_edit_draw (cmdmap), _sm_input_fn (smartmenu, every "Select:" menu prompt), _print_input_line (browse, "Select:"),
   _multi_print_input_line (viewport, "Item numbers:" / "Group numbers:"), settings_ui "Select: $buf" (block redraw by row count
   and the final "Select: u"). All five have the bug. The dim hint row under the prompt (_cm_hint_row, _input_hint_sync) prints
   text that can be wider than the screen too; _cm_hint already cut it by characters, not by cells (emoji/CJK are 2 cells).
   Not affected: the loading bar (clips to its own width), full-screen redraws that print fixed short rows.
(Verified in a pty with my own VT emulator on Linux, widths 30/40/50/80/120, also with non-ASCII/emoji text. NOT tried on a real
phone. tests/cheatcode.sh fails the same way before and after my change here (needs installed commands), so it says nothing.)

CAUSE
Every typed-line editor assumed prompt+text fit on one terminal row and redrew it in place with \r / \033[K / \033[nD. When a long
paste (or a long prompt) wraps on a narrow screen, those codes only touch the last row, so each keystroke added a new copy.

FIX
- engine/bashbasicsbyvk_viewport.sh: new shared helpers _bvk_is_ascii, _bvk_dispw (display width: emoji/CJK = 2, ANSI ignored),
  _bvk_cols, _bvk_clip (cut a hint to the row) and _bvk_fit_input (keeps the editing row to ONE line: the text scrolls sideways
  inside the row, "<" marks hidden text on the left, the cursor stays correct, the prompt is shortened only on tiny screens).
- cmdmap _cm_edit_draw / _cm_line_edit: draw through _bvk_fit_input; a prompt that leaves < 24 cells for typing is printed once on its
  own line(s) and the typing row becomes "> "; the hint row is clipped by cells; the final cursor move uses the fitted count.
- smartmenu _sm_input_fn, browse _print_input_line, viewport _multi_print_input_line, settings_ui (block + final line): same helper.
  Each keeps the old code as fallback when the helper is not loaded.
- tests/wrap_input/run.sh (new; harness.sh + emu.py): pastes the real link at 30/40/50/80 columns into the cm and browse editors and
  requires <= 1 prompt row and the text intact. Fails on the old code (3-9 rows), passes now.
Lesson: never redraw an input row with \r + \033[K assuming one row. If text can be longer than the screen, either window it into one
row (_bvk_fit_input) or print with real wrapping and redraw by counting rows. Any NEW typed-line editor must use _bvk_fit_input.
Not changed: the text of the typed value is never altered, only what is drawn; the returned value is the full pasted link.
